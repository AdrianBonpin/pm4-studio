# 02 — 125 kHz: Read · Write · Clear · Clone · Batch

**Ticket criterion:** each of the five 125 kHz modes at both sizes, including a
readout, a confirmation, and the confirmation that destroys a Tag.

**Re-captured on `ticket/06-e2e-shell-and-125khz`** (integration `d6eadd2`), from
`http://localhost:1420/e2e.html?lf=source`, at 980×760 and at the 900×700
minimum, with the fixture standing at the invoke boundary. Every image in this
file is one taken in that pass; nothing here survives from the previous capture.

**The five modes are the glossary's words** (`LF_MODE_LABEL` in
`src/lib/lfModes.ts`): **Read · Write · Clear · Clone · Batch**. Inside Clear
there are two operations, and they are different things: **Clear** is the
everyday one, which overwrites the Identity with a placeholder and leaves a live,
writable Tag, and **Destroy** is the deliberate, destructive one, which is a
separate entry point on Clear's first screen rather than a second button on
Clear's confirmation. There is no factory restore and no unlock behind either
(`GLOSSARY.md`, "Clear" and "Destroy").

## The Clear confirmation, quoted

The confirmation states six things before the button, and the three the spec
requires are facts 4, 5 and 6 (`lf-clear-confirmation-980.png`):

> **This Reader cannot tell whether a tag will accept a write.** A 125 kHz reply
> carries no tag family and no writability flag, and there is no command that asks
> a tag whether it will take a write. Every command that would answer the question
> is itself a write, so no check exists — not in this app, and not in this
> protocol.

> **A tag already written once may refuse forever.** A T5577 that has already been
> written may permanently refuse every later write while still reading back the
> Identity it carries. This Reader cannot tell a tag that will refuse from one that
> will accept.

> **Only clear a tag you can afford to lose.** Clearing should leave a live tag,
> and the payload it writes is the same shape as the clones this app performs
> routinely. That is an argument, not a measurement: no cleared tag has yet been
> confirmed to take a new Identity. Treat the attempt as one you would not mind
> losing.

The first three facts are what Clear does and what it does not: the Identity on
the Tag now *is overwritten for good* and cannot be recovered from the Tag
afterwards; the Tag *stops being a credential*, because the placeholder no
building system issues will not open anything; and the Tag *stays a tag, and stays
readable*, so a Clone or an authored Identity can be written onto it afterwards —
though whether that next write is accepted is the Tag's answer, as it is for any
write.

Two claims the previous edition of this report made about the confirmation no
longer hold, and are corrected rather than carried:

- **The panel does not deny a factory restore.** That denial is one of this
  Reader's capability limits and is stated once, in Settings → Diagnostics →
  Capability limits (*"Factory restore and unlock — Not possible."*). Repeating it
  in the panel was what the retirement of the old name was for.
- **A Clear does not leave a Tag that reads as empty.** It leaves the **Cleared**
  placeholder — customer `0x00`, facility `0xFF`, card `0xFFFF`, identity
  `00 00 FF FF FF` (`Identity::CLEARED` in `src-tauri/src/identity.rs`) — which
  reads back as an Identity, and that is what keeps the Tag writable. A Tag that
  reads as nothing is what a **Destroy** leaves, and `DESTROY_FACTS` says so where
  Destroy is offered.

## The Destroy confirmation, quoted

Its heading is its own (`Permanently destroy the tag holding 55 00 84 82 12?`) and
its four facts are starker than Clear's on purpose:

> **This permanently disables the tag.** The tag will never accept data again.
> This is not a caution about a possible outcome: every tag this app has written
> this way has permanently refused every later write, and nothing in this app can
> undo it.

> **It cannot be recovered or reused.** There is no factory restore and no unlock
> in this protocol. The tag cannot be written again — not by a Clone, not by an
> authored Identity, and not by running this again.

> **Every reader will still see it.** A destroyed tag keeps answering readers
> while it refuses all data. Reading it back and getting a reply therefore does
> not mean it still works.

> **Only use this on a tag you are finished with.** Clear is the operation for a
> tag you want back. Destroy is the one for a tag you want gone, and it takes the
> tag with it.

## The refusal, and the alphabet leaving the seam

Confirming the Clear on the fixture's written-once T5577 produced the app's own
outcome — *this tag will not accept writes*, with the likely cause named, and
*Still on the tag: 55 00 84 82 12* under it (`lf-clear-refusal-980.png`) — and,
read at the device boundary, exactly this sequence, with the times measured from
the first frame:

```
lf_poll  0 ms
beep     0 ms
lf_clear   621 ms
beep      621 ms
beep     1023 ms
beep     1425 ms
led_off  3427 ms   ← 2 002 ms after the last chirp
```

Three chirps 400 ms apart, then the LED released two seconds after the last one,
which is the attention symbol's hold (`CHIRP_GAP_MS` and `ATTENTION_LED_HOLD_MS`
in `src/lib/chirpSequence.ts`). The previous edition of this report said
"2 600 ms later", which was the wrong interval and the wrong thing to measure: the
hold is 2 000 ms from the last chirp, not 2 600 ms from some other point.

**This is the app's bookkeeping and nothing more.** It is not evidence that a
buzzer sounded or an LED lit; criterion 5 of the ticket is unrun (see the hardware
checklist).

## Naming: what this report used to call things

The previous edition of this report gave the everyday operation a name
`GLOSSARY.md` has retired, and raised a finding (F4) about the panel using a
different word again. Both described an interface that no longer exists: the
switcher's option, the panel's heading, the control that starts it, the confirm
button, the repeat control and the page subtitle all say **Clear** now, and the
destructive write is **Destroy** behind its own entry point. F4 is withdrawn, and
the words it was written in are kept in [08-findings.md](08-findings.md) with its
corrected fix note. Nothing in this report calls the everyday operation anything
but Clear.

## Observations

1. **The Write confirmation's own controls are below the fold at both sizes.**
   Measured: its action row (*Read the tag, then write* / *Change the values*) sits
   at y=771–805 at both 980×760 and 900×700, while the pane is 724px tall at the
   first and 664px at the second, with 793px of content. Reaching Write means
   scrolling to it. This is the failure mode F3 fixed for the Erase confirmation
   and it now lives here instead. The Clear and Destroy confirmations do not have
   it — their buttons are inside the window in both images, because each focuses
   *Keep the tag as it is* on entry, which scrolls the pane to them.
2. **The default bottom-right corner collides with a confirmation's controls.**
   Three instances, all with the default corner: at 900×700 the Destroy
   confirmation's read message covers part of *Keep the tag as it is*
   (`lf-destroy-confirmation-900.png`); the Clone confirmation carries two stacked
   messages that cover *Tap a different tag* and *Cancel*
   (`lf-clone-confirmation-900.png`); and at 980×760 the same corner covers a
   paragraph of the Write confirmation's explanation. This is O1 in
   [08-findings.md](08-findings.md), with different evidence: the message the user
   cannot get out of the way is now over a different confirmation's controls.
   Still not filed as a defect, for the reason O1 gives — a corner is where the
   user put it, choosing another is one click, and a success message clears in
   four seconds.
3. **Destroy's confirmation sits under a section heading that says *Clear a tag*.**
   The heading names the mode, and Destroy is one of the mode's two operations, so
   the words are both true; it reads slightly oddly over the reddest thing on the
   screen. Copy nuance, not a defect, and changing it would mean a heading that
   changes under the user mid-flow.
4. **A Clear can be reached, and refused, without the Tag being touched.** The
   refusal image is the one place in this set where the app says what happened
   rather than what is about to: the inline notice, the corner message and
   *Still on the tag* all state the same thing, and the confirm button is gone
   rather than disabled.

## What is *not* established here

Nothing about a real T5577, a real Clear, a real Destroy, a real read, or a real
refusal. The fixture models writability as a boolean because that is the only way
to draw the refusal; whether a given chip refuses is exactly the thing that needs
hardware. The Clone confirmation's `77 00 AB CD EF` is the fixture's second
Tag and its `Replace … with …` wording is the app's, not an observation.
