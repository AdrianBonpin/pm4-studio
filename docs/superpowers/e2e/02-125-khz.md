# 02 — 125 kHz: Read · Write · Reset · Clone · Batch

**Ticket criterion:** each of the five 125 kHz modes at both sizes, including a
readout, a confirmation, and the Reset confirmation carrying its three
writability caveats.

the guards, the words and the chirp counts are the app's.

## The Reset confirmation, quoted

The three caveats the spec requires, all present, in the confirmation and before
the button (`lf-reset-confirmation-980.png`):

> **This Reader cannot tell whether a tag will accept a write.** A 125 kHz reply
> carries no tag family and no writability flag, and there is no command that asks
> a tag whether it will take a write. Every command that would answer the question
> is itself a write, so no check exists — not in this app, and not in this
> protocol. Nothing here can look at the tag and tell you first.

> **A tag already written once may refuse forever.** A T5577 that has already been
> written may permanently refuse every later write while still reading back the
> Identity it carries. This Reader cannot tell a tag that will refuse from one that
> will accept.

> **Only attempt this on a tag you can afford to lose.** The write is the test, so
> there is no cheaper way to find out whether this tag accepts one. If you need the
> tag, do not put it here — the app cannot make the attempt safe.

Plus the two supporting facts the spec also asks for: that a blanked tag reads as
empty rather than as a failure, and that blanking is not a factory reset and does
not unlock the tag.

## The refusal, and the alphabet leaving the seam

Confirming the Reset on a tag that will not accept writes produced the app's own
outcome — *this tag will not accept writes*, with the likely cause named — and,
read at the device boundary, exactly this sequence:

```
lf_poll, beep, lf_blank, beep, beep, beep … [2 600 ms later] … led_off
```

Three chirps, then the LED released two seconds later. **This is the app's
bookkeeping and nothing more.** It is not evidence that a buzzer sounded or an LED
lit; criterion 5 of the ticket is unrun (see the hardware checklist).

## Findings raised by this area

- **F4 — Reset is called "Blank" in its own panel.** The mode pill says *Reset*;
  the panel heading says *Blank a tag*, its first control says *Read the tag to
  blank*, the confirm button says *Blank this tag permanently*, and the page
  subtitle says "…or blank a tag". `GLOSSARY.md` lists "blank (as a verb)" on
  Reset's *Avoid* line. Follow-up ticket:
  `docs/tickets/studio-redesign-followups/reset-is-called-blank-in-its-own-panel.md`.
- **Observation — the Write confirmation's third note reads oddly on a Blank.**
  The note explains that a tag already carrying this Identity is refused, which
  is true and useful, but on a Blank it is reassurance about a case that has not
  happened. No ticket: it is copy nuance, not a defect.
- **Observation — the default bottom-right corner overlaps a confirmation's
  cancel control at 900×700.** See [08-findings.md](08-findings.md).

## What is *not* established here

Nothing about a real T5577, a real Blank, a real read, or a real refusal. The
fixture models writability as a boolean because that is the only way to draw the
refusal; whether a given chip refuses is exactly the thing that needs hardware.
